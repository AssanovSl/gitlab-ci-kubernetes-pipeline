# CI/CD Pipeline for Kubernetes Microservices

Практический проект по построению CI/CD pipeline для микросервисного приложения — от автоматической сборки изменённых сервисов до функционального тестирования и обновления приложения в Kubernetes.

Полноценный CI/CD pipeline для микросервисного приложения, автоматизирующий сборку изменённых сервисов, публикацию Docker-образов, изолированное тестирование в Kubernetes и обновление staging-окружения.

### Поставленные цели

* Настроить GitLab Runner для выполнения CI/CD задач в Kubernetes.
* Реализовать автоматическую сборку только изменённых микросервисов.
* Настроить сборку Docker-образов и публикацию в Docker Hub.
* Организовать передачу артефактов между стадиями pipeline.
* Создавать изолированное Kubernetes-окружение для функционального тестирования.
* Использовать Kustomize для подготовки тестовых манифестов.
* Автоматизировать функциональное тестирование через Postman / Newman.
* Реализовать автоматическое удаление временного test-окружения.
* Настроить staging-развёртывание через Helm.
* Проверить работу Rolling Update при обновлении Docker-образов.

### CI/CD Pipeline

1. **Stage 1. Build**

Стадия запускается автоматически для feature-веток.
Pipeline определяет, какие микросервисы были изменены с момента предыдущего коммита.  
Для изменённых сервисов:  
* выполняется сборка Docker-образа;
* выполняется авторизация в Docker Hub;
* образ публикуется в registry;
* формируется список изменённых сервисов;
* сохраняется информация об актуальных образах в артефактах.

Если в коммите не изменился ни один микросервис, новые Docker-образы не создаются.  
Результаты стадии передаются в следующие stages через GitLab CI artifacts.

2. **Stage 2. Test**

После успешной сборки создаётся временное Kubernetes-окружение для тестирования.  
Для каждого запуска pipeline используется отдельный namespace.  

Пайлайн используя **Kustomize**:
* получает информацию об актуальных Docker-образах из артефактов Build;
* формирует итоговый Kubernetes-манифест;
* адаптирует конфигурацию приложения для временного окружения;
* отключает постоянное хранилище PostgreSQL для изолированных test-запусков.  
После развёртывания приложение проверяется через *Postman / Newman*.  
Для обращения между сервисами используются Kubernetes DNS-имена:
`service.namespace.svc.cluster.local`

После завершения тестов временный namespace удаляется.

Итоговый manifest сохраняется в качестве артефакта pipeline и позволяет проверить фактически использованные версии Docker-образов.

3. **Stage 3. Staging**

После успешного прохождения функциональных тестов выполняется обновление staging-окружения через **Helm**.  
Пайплайн подставляет актуальные версии Docker-образов в конфигурацию Helm и выполняет обновление приложения.

Kubernetes обнаруживает изменение образов и выполняет Rolling Update.

### Особенности реализации

**1 Сборка только изменённых сервисов**

Pipeline анализирует изменения в Git и определяет список затронутых микросервисов.  
Таким образом, изменение одного сервиса не приводит к пересборке всех Docker-образов.

**2 Изолированное test-окружение**

Каждый запуск функциональных тестов выполняется в отдельном Kubernetes namespace.  
После завершения тестов окружение удаляется, что позволяет повторно запускать pipeline без накопления временных ресурсов.

**3 Проверка отсутствия изменений**
Если коммит не содержит изменений микросервисов, Build не создаёт новые Docker-образы, а Test пропускает развёртывание и тестирование.

**4 Kustomize для test-окружения**

Базовые Kubernetes-манифесты сохраняются неизменными.  
Необходимые изменения для временного окружения реализованы через Kustomize overlay.

### Ограничения

* Проект выполнен в учебных целях и использует упрощённую схему CI/CD.
* Для Docker-образов используется тег `latest`, но для production рекомендуется использовать immutable tags, например commit SHA или release version.
* Test-окружение использует временное хранилище PostgreSQL вместо PersistentVolume.
* Staging-развёртывание выполняется в одном Kubernetes-кластере.
* В проекте не реализованы production-окружение и ручное approval перед production deployment.
* Секреты и credentials должны храниться во внешнем secret management / CI/CD variables и не должны находиться в публичном репозитории.

### Результаты  
Реализован автоматизированный цикл Build → Test → Staging для микросервисного приложения.

В рамках проекта:
настроен GitLab Runner в Kubernetes
- реализована сборка *только* изменённых микросервисов
- настроена *публикация* Docker-образов в registry
- реализована передача данных между stages через *artifacts*
- созданы ephemeral Kubernetes *test-окружения*
- автоматизировано функциональное *тестирование* API через Postman / Newman
- реализовано автоматическое удаление *test-окружений*
- *Kustomize* используется для подготовки test manifests
- *Helm* используется для staging deployment
- проверено обновление приложения через Kubernetes *Rolling Update*.
